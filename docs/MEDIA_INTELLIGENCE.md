# 素材校验、媒体证据与多模态理解

## 1. 目标

素材理解不能只依赖文件名、完整逐字稿或固定间隔抽帧，也不能假装任何单一模型已经逐帧准确理解全部音视频。

本方案采用：

> **提交前权威校验 + 技术探测 + FunASR + 镜头检测 + 分层抽帧 + 本地确定性音频分析 + 云端多模态理解 + 候选区间密集复核。**

这些模块生成证据；`video-source-understanding` 负责专业综合；`video-edit-director` 才决定最终选片和结构。

## 2. 责任边界

| 责任 | 实现 |
|---|---|
| 浏览器快速预检 | Web 前端 |
| 文件完整性、媒体流、时间轴、解码和稳定工作副本 | Upload Validation Service + FFmpeg/ffprobe |
| 代理、音频提取、抽帧和联系表 | Media 模块 / `davinci-engine-mcp` |
| 中文语音、VAD、标点、说话人和时间码 | 本地 FunASR Adapter |
| 镜头边界候选 | PySceneDetect 或等价 Detector |
| BPM、Beat、Onset、能量、LUFS、True Peak、静音候选 | `davinci-engine-mcp` 中的确定性分析模块 |
| 事件、动作、表情、镜头运动、环境声、音乐情绪和声画关系 | `MultimodalAnalyzerPort` 当前实现 |
| 证据统一、冲突和绝对时间码 | Evidence Fusion Service |
| 完整语义单元、上下文和安全取用范围 | `video-source-understanding` |
| 选片、结构和剪辑决定 | `video-edit-director` |

## 3. 总体链路

```text
用户文件
  ↓
上传与服务端权威校验
  ↓ ready
内容身份与技术探测（后续复用）
  ↓
稳定工作副本 / 分析代理 / 音频提取
  ├── FunASR Transcript
  ├── Shot Detection
  ├── Layered Frames / Contact Sheets
  ├── Rhythm / Loudness / Silence Evidence
  └── Multimodal Evidence
  ↓
Evidence Fusion
  ↓
Source Understanding Skill
  ↓
SourceUnderstanding
  ↓
Edit Director
  ↓
候选区间请求与密集复核（按需循环）
```

## 4. 提交前素材校验

### 4.1 浏览器预检

前端可以立即检查：

- 文件是否为空；
- 文件大小和扩展名；
- 是否重复选择；
- 浏览器能够读取的基本时长和类型；
- 是否超过产品配置限制。

前端预检只用于快速提示，不能把素材标记为最终可用。

### 4.2 上传 staging

文件先写入项目 staging 目录。上传完成前状态为 `uploading`；完成后进入 `validating`。

系统必须确保：

- 文件写入完整；
- 文件大小稳定；
- 内容哈希能够计算；
- 校验期间文件不会被用户或同步软件替换；
- Nextcloud 或其他云盘引用已经本地化，不是在线占位。

### 4.3 权威技术探测

使用 ffprobe 或等价实现读取：

- 容器和编码；
- 视频、音频和字幕流；
- 时长；
- 帧率与时间基准；
- 分辨率、像素比例和旋转；
- 音频采样率和声道；
- 色彩信息；
- 是否存在明显可变帧率或异常时间戳；
- 是否能够稳定 seek。

### 4.4 实际解码验证

仅有 metadata 不足以证明文件可用。

至少验证：

- 开头；
- 中间；
- 结尾；
- 关键源视频按实现策略完成更完整的错误扫描；
- 图片能完整解码；
- 音频能持续解码且时长合理。

发现错误时，返回具体时间范围和原因。

### 4.5 稳定工作副本

遇到以下问题时，系统先尝试生成稳定工作副本：

- 可变帧率；
- 不稳定时间戳；
- Resolve 不适合直接使用的编码；
- 异常旋转、采样率或像素格式；
- seek 行为不可靠。

要求：

- 不覆盖原文件；
- 记录源到工作副本的时间映射；
- 工作副本必须重新通过解码验证；
- 无法建立可靠映射时不能让 Skill 输出精确源时间范围。

### 4.6 结果

- 原文件或稳定工作副本通过：`ready`；
- 无法读取或修复：`invalid`；
- `ready` 可以附带分辨率、无音轨、曝光或处理时间等警告。

上传校验生成的内容哈希、技术探测和工作副本必须被后续分析复用。

## 5. 素材身份和缓存

每个源文件使用内容哈希作为稳定身份的一部分。

缓存键概念：

```text
source content hash
+ analyzer identity/version
+ analysis configuration
```

提交任务时再次检查：

- 文件仍存在；
- 内容哈希未变化；
- 工作副本仍可访问；
- 本次运行使用的素材都是 `ready`。

## 6. 分析代理

### 6.1 目的

- 降低云端多模态上传和处理成本；
- 保留完整音频和时间关系；
- 统一长宽、编码和 seek 行为；
- 为联系表和密集窗口提供稳定输入。

### 6.2 要求

- 不改变总时长和音画同步；
- 记录代理与源素材的时间映射；
- 默认使用适合分析的中等分辨率，不覆盖源文件；
- 小文字、UI 和细节项目可以生成更高分辨率局部代理；
- 快速动作区间可以生成慢放分析代理，但最终范围仍映射回源时间码。

## 7. FunASR 本地转写

### 7.1 运行方式

FunASR 模型已经由项目在本机 `models` 目录准备，运行时不自动下载。

配置概念：

```text
FUNASR_MODEL_ROOT=<本机 models 目录>
FUNASR_ASR_MODEL=<本机 ASR 模型目录>
FUNASR_VAD_MODEL=<本机 VAD 模型目录>
FUNASR_PUNC_MODEL=<本机标点模型目录>
```

实际模型权重不提交 Git。仓库只保留模型 manifest、配置示例和健康检查代码。

### 7.2 启动健康检查

Worker 启动后必须验证：

- 配置目录存在；
- 必要配置和权重文件完整；
- 模型能够加载；
- 能处理标准测试音频；
- 输出至少包含可用文本和时间信息；
- 模型身份、版本和配置哈希能够记录。

健康检查失败时，与转写相关的任务不能开始；Web 显示明确系统问题。

### 7.3 输出责任

至少提供：

- 带开始/结束时间的句子或语义候选；
- 标点；
- VAD 语音区间；
- 可选说话人标签；
- 可选词级或字符级时间信息；
- 专有词热词支持；
- 识别置信和无法确认部分。

转写用于：

- 素材语义索引；
- 对白搜索；
- 字幕候选；
- 说话人和句子边界辅助；
- 与多模态声画证据交叉验证。

ASR 标点和 VAD 不是最终剪辑边界。人物停顿、呼吸、反应和动作可能跨越文本句子。

### 7.4 统一转写来源

中文项目以 FunASR 结果为统一可搜索转写，不再维护一套独立 Whisper 转写作为业务真相。其他分析器读取同一结果。

## 8. 镜头检测

镜头检测负责找到硬切、明显场景变化和渐变候选，主要用途是：

- 建立概览；
- 对齐抽帧；
- 分组多模态分析片段；
- 发现长镜头和快速切换区域。

Detector 输出不等于语义单元。一个镜头中可以包含问题、回答、动作、结果和反应；多个镜头也可以共同构成一个完整语义单元。

快速镜头运动容易造成误检，需使用自适应检测、最短镜头约束和后续证据校正。

## 9. 分层抽帧

### 9.1 概览层

每个镜头至少抽取开始附近、中间和结束附近的代表帧。长镜头按时间间隔补充。

### 9.2 语义边界层

在以下位置附近补充帧：

- 句子开始和结束；
- 长停顿前后；
- 说话人变化；
- 重要关键词；
- 多模态分析检出的状态变化；
- 镜头运动开始和结束。

### 9.3 候选密集层

当下游拟使用某个范围或切点时，对候选前后生成密集证据：

- 扩展前后余量；
- 提高抽帧频率；
- 生成带时间码联系表；
- 必要时生成慢放代理；
- 对动作准备、关键相位、结果和反应分别检查。

密集层按需生成，不对全部长素材逐帧处理。

## 10. 确定性音频分析

`davinci-engine-mcp` 内部提供：

### 10.1 节拍与音乐

- BPM 候选；
- Beat 时间；
- Onset 时间和强度；
- 能量包络；
- 音乐可裁切候选；
- 乐段变化的数值线索。

这些数据用于定位和比较，不自动决定切点。拍号、首拍和能量峰值都只是专业声音 Skill 的候选证据。

### 10.2 响度与 Mix 数据

- LUFS；
- True Peak；
- Loudness Range；
- 对白、音乐和音效的基础层级测量；
- Ducking 候选。

技术测量不等于混音审美。

### 10.3 静音候选

通过声能和持续时间发现可能可压缩的区间。它只输出候选，不自动删除，因为停顿可能承担表演、思考、喜剧、情绪或空间作用。

## 11. 云端多模态分析

### 11.1 Port 与当前实现

```text
MultimodalAnalyzerPort
  └── OpenAICompatibleMultimodalAdapter
```

当前配置模型 ID：

```text
MULTIMODAL_MODEL=gemini-3.5-flash
```

其他配置只从本机安全环境读取：

```text
MULTIMODAL_BASE_URL=<OpenAI-compatible endpoint>
MULTIMODAL_API_KEY=<secret>
```

业务模块不得写死供应商 URL、密钥或具体 SDK。

### 11.2 能力探测

模型列表中出现 `gemini-3.5-flash` 只说明端点接受这个路由 ID，不证明全部模态可用。

系统启动时必须实际测试：

- 文本；
- 图片；
- WAV 音频；
- 5～10 秒带声音 MP4；
- 同时理解视频画面和音轨；
- 结构化 JSON 输出；
- 超时、文件大小和并发行为。

探测结果记录为能力矩阵。只有实测通过的模态才能进入任务分析 Profile。

### 11.3 输入策略

- 上传分析代理而非默认上传原始高码率文件；
- 每次请求优先只包含一个视频片段；
- 按镜头组和语义连续性切成可管理区间；
- 相邻区间保留少量重叠；
- 同时提供对应 FunASR 转写和任务上下文；
- 用户未授权云端分析时不得上传；
- 第三方反代的实际视频提交格式由 Adapter 封装，不能泄漏到业务层。

### 11.4 输出责任

多模态模型输出结构化 MultimodalEvidence，至少覆盖：

- 时间范围；
- 可观察事件和状态变化；
- 人物、对象和动作；
- 动作准备、发生、完成和反应；
- 表情和情绪线索；
- 镜头景别、构图和运动；
- 环境声、动作声、音乐和静音；
- 声音与画面的关系；
- 画内文字和 UI；
- 可能的上下文依赖；
- 不确定性和需要密集复核的位置。

多模态模型只生成证据，不决定最终选片和 Resolve 操作。

### 11.5 时间精度边界

第三方反代对视频的采样策略、时间码精度和音轨处理方式必须以实测为准，不能根据模型名称推断。

无论探测结果如何：

- 不把模型返回的时间码直接视为帧级切点；
- 快速动作使用更短窗口、密集本地帧或慢放代理；
- 重要候选边界进行二次复核；
- 小文字和 UI 使用高分辨率图片证据；
- 多模态观察与 FunASR、镜头图和本地帧冲突时保留冲突。

### 11.6 降级策略

- `supports_video_audio=true`：使用直接音视频证据；
- 只支持图片：使用联系表 + FunASR + 本地音频分析，并明确标记为 `image_transcript_mode`；
- 视频或音频是当前项目质量硬要求但端点不支持：禁止开始或等待能力恢复；
- 允许降级时，Web 和结果说明必须披露限制；
- 不允许把图片+转写模式声称为直接连续音视频理解。

### 11.7 隐私与密钥

- Web 明确告知云端上传范围；
- 尽量只上传必要代理和片段；
- 远端临时文件按提供方能力清理或过期；
- API Key 只保存在 `.env`、系统凭据或受控秘密存储；
- Key 不得出现在日志、错误页面、截图、文档和 Git；
- 发生疑似泄漏时立即轮换。

## 12. Evidence Bundle

每份素材生成可版本化的 Evidence Bundle。概念上包含：

```text
evidence/<asset-id>/
├── manifest
├── media-info
├── validation
├── transcript
├── shots
├── audio-analysis
├── multimodal-observations
├── contact-sheets/
└── dense-windows/
```

它不是一份巨型 Markdown。具体内容使用结构化文件和媒体引用保存。

每条关键证据必须能回到：

- 源素材和内容哈希；
- 时间范围；
- 生成器和版本；
- 原始观察或测量；
- 当前分析模式；
- 是否存在冲突或未知。

## 13. Evidence Fusion

Evidence Fusion Service 负责：

- 统一源时间码；
- 合并同一时间范围的转写、画面、声音和镜头信息；
- 保留不同分析器的来源；
- 标记冲突，不做无证据覆盖；
- 建立证据覆盖图；
- 为 Skill 提供按时间、人物、关键词和镜头查询；
- 生成需要补充证据的范围。

它不作剪辑审美决定。

## 14. Source Understanding Skill 调用

当基础证据完成后，Workflow：

1. 创建 SkillInvocation；
2. 通过 Codex App Server `turn/start` 显式调用 `video-source-understanding`；
3. 附加关键联系表为本地图片；
4. 提供 `video-project-mcp` 作用域凭证；
5. 使用 SourceUnderstanding 输出 Schema；
6. 校验时间范围、证据引用和未知标记；
7. 若 Skill 请求补充区间，Workflow 生成 dense window 并再次调用；
8. 保存最终 SourceUnderstanding。

Codex 不直接接收原始视频作为通用 turn 输入，因此 Skill 必须诚实地依赖多模态音视频证据、转写和图片，不得声称自己已逐帧观看源素材。

## 15. 缓存与增量更新

增量规则：

- 上传校验已完成：复用内容哈希、技术探测和工作副本；
- 文件不变：复用技术探测；
- 只更换多模态模型或反代：重做多模态证据，不重做 FunASR；
- 只更新热词：重做转写和相关融合；
- 只请求新候选边界：生成对应 dense window；
- 用户纠正说话人或事实：保留原始机器结果并叠加用户更正；
- 项目目标变化：通常不重做底层证据，但重新运行专业理解和剪辑计划。

## 16. 首期质量验收

至少准备：

- 中文单人口播；
- 双人采访；
- 屏幕录制加解说；
- 破损或时间戳异常素材；
- 快速动作片段；
- 音乐驱动短片；
- 含画内文字和竖屏重构需求的素材。

验证：

- 不可解码素材在 Web 提交前被阻断；
- 可修复素材生成稳定工作副本后成为 `ready`；
- 转写时间码和说话人可用；
- 镜头边界可回链；
- FunASR 使用本地模型且不会意外在线下载；
- 反代能力探测能真实区分图片、音频、视频和结构化输出；
- 配置的 `gemini-3.5-flash` 能力与系统启用模式一致；
- 多模态证据能说明主要事件、动作和声画关系；
- 快速动作不会仅凭稀疏模型观察确定切点；
- SourceUnderstanding 不产生残句、半个动作和错误因果；
- 证据不足时系统能请求最小补充范围；
- 相同素材重复运行能命中缓存；
- 更换分析器不会破坏其他证据。
